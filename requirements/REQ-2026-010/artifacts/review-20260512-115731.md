## Major（强烈建议修复）

### [F-7 + F-7b] 捆绑：sub_workflow 把 sub_run_dir 当仓库根 + 测试反向锁错误

**位置**：
- `scripts/lib/workflow_dispatcher.py:436`
- `tests/lib/test_workflow_dispatcher_f011.py:217-238`

**问题描述**：
`_dispatch_sub_workflow_node` 调用 `workflow_run.main(args_list, repo_root=sub_run_dir)` 把子 run 目录当仓库根传入；而 `workflow_run.py:195 root = repo_root or REPO_ROOT`，`workflow_run.py:209 workflow_dir = root / ".claude" / "workflows"`——sub run 启动后会去 `sub_run_dir/.claude/workflows/` 找模板必失败。

测试 `test_sub_workflow_passes_correct_repo_root_to_main` 用 mock 整体替换 `workflow_run.main` 后断言 `repo_root == sub_run_dir`，把这个错误行为反向锁定成合同——构成 review 红线。

虽然 F-011 标"深度联动留后续"未要求真跑通子 run，但作为最小实现不应埋入测试可见的反向锁定。

**建议**：
1. dispatcher 改为 `workflow_run.main(args_list, repo_root=root)`（仓库根）；子 run 目录通过另一参数或环境变量传递（如新增 `run_dir_override` 或 `WORKFLOW_RUN_DIR`）。
2. 测试断言翻成 `assert captured_kwargs.get("repo_root") == root`。
3. 改完跑 pytest 通过即可。

### [F-8] loop_counters 写事件不一致：rebuild 重放丢增量

**位置**：
- `scripts/lib/workflow_dispatcher.py:384`（_dispatch_loop_node 写事件）
- `scripts/lib/workflow_continue.py:266`（内存 +1 不写事件）

**问题描述**：
`workflow_continue.py:266` 在 loop_continue 返回后做 `run_state.loop_counters[node_id] += 1`，仅内存递增，不写 jsonl 事件。`run_state.py:208-210` rebuild 只从 jsonl 重放 `data.iteration`。崩溃恢复后 rebuild 出的 loop_counters = 最后一条 `loop_iteration_completed.data.iteration`，比实际少 1 → 下次 continue 会重复执行同 iteration。

当前 loop 节点是占位 stub 无业务副作用，未爆；下游业务接入后会暴雷。根因模块属 F-008 范围，但本 PR 是首次让 loop 事件流真正驱动 RunState rebuild。

**建议**：
本 PR 不在 dispatcher 端硬改（跨 feature scope），但在 `requirements/REQ-2026-010/notes.md` 显式登记 follow-up：
> F-008 收口前修复：loop_counters 改为只信 jsonl rebuild——workflow_continue.py:266 不再内存 +1，由 dispatcher 写 loop_iteration_started 时记录"将要执行的 iteration"，rebuild 重放即可。

## Minor（改进建议）

### [F-1] dispatch_node 圈复杂度逼近阈值

**位置**：`scripts/lib/workflow_dispatcher.py:110-167`

dispatch_node 圈复杂度 9（阈值 10），7 类节点 if/elif 链 + try/except。当前 DispatchOutcome 7 类封闭枚举不易扩展，短期可控。

### [F-4] dispatch_node except 丢栈

**位置**：`scripts/lib/workflow_dispatcher.py:155-165`

`except Exception as exc` 只记 `str(exc)`，非 WorkflowError 类内部 bug 无 traceback 可追溯。

**建议**：区分异常路径——`except WorkflowError` 走 str；`except Exception` 用 `logging.exception` 记完整堆栈再压扁到 jsonl `data.error`。

### [F-5] workflow_run.main 异常被顶层吞

**位置**：`scripts/lib/workflow_dispatcher.py:436`

workflow_run.main 内部少数残余异常路径（如 glob OSError）会穿透到 dispatch_node L155 被压缩，丢失子 run 启动失败细分类别。

**建议**：_dispatch_sub_workflow_node 内显式 try/except，记 traceback 后包成 WorkflowError 上抛，保留启动失败上下文。

### [F-6] loop 节点事件多写 run_id 字段

**位置**：`scripts/lib/workflow_dispatcher.py:386-398`

_dispatch_loop_node 写 loop_iteration_started/completed 时附带 `run_id` 字段；skill/prompt/bash/approval 节点均不写。风格不一致。

**建议**：去掉 loop 事件的 run_id 字段，与其他 6 类节点对齐。

### [F-9] 缺连续 N 次序列断言

**位置**：`tests/lib/test_workflow_dispatcher_f011.py`

features.json F-011 acceptance #1 字面要求 outcome 序列 = `[loop_continue]*(N-1) + [loop_done]`。现 5 个独立子用例分别断言，缺单一连续序列。

**建议**：补一个 `test_loop_dispatch_until_done` 用 for 循环连续调用 _dispatch_loop_node N 次（每次手动 +1 模拟 workflow_continue 行为），收集 outcomes 列表，断言整体序列。
