## Required Fixes（major × 2，必修阻塞合入）

### F-CR-014 · 缺 created_at + st_mtime 二次校验（design_consistency）

- **file**：`scripts/lib/path_lock.py:155-214`
- **设计契约源**：`detailed-design.md:193`（§2.3 lock 文件格式）+ `:1613`（§5.1 实现细节）+ `:1887`（R-6 风险表 1e-7/op 概率目标）
- **现状**：`grep mtime|st_mtime path_lock.py` 0 命中；残锁清理仅靠 `_is_pid_alive`（kill -0 ESRCH）单层防护，pid 复用窗口（macOS pid 回绕 ~3 小时）无缓解
- **影响**：违背设计承诺的 "误清概率 ≤ 1e-7/op" 目标；pid 复用场景下可能误清活锁
- **修复建议**：在 `_is_pid_alive` 返 False 后追加 `lock_path.stat().st_mtime - parse_iso(created_at).timestamp() >= 1.0` 校验；不满足则保守视为活锁

### F-CR-004+005 · acquire / retry 路径 fd 泄漏（error_handling + security）

- **file**：`scripts/lib/path_lock.py:176-178 + 196-208`
- **现状**：`fd = os.open(...)` 后立即调 `_try_fcntl_lock(fd)`；`_try_fcntl_lock`（98-108）只兜底 BlockingIOError + EAGAIN/EWOULDBLOCK，其他 OSError（EBADF/EINVAL/EDEADLK 等）走 `raise` 重抛——此时 fd 未关，传播到 acquire 调用方
- **第二处**（retry 路径）：第 200-206 行 `retry_data` 非 None 时直接 raise LockBusyError，未在 raise 前 `os.close(fd)`；仅第 207 行的 None 分支 close
- **影响**：fd 泄漏 + 持有 BSD flock 让本进程后续 acquire 看到诡异自持锁状态；长跑进程资源耗尽风险
- **修复建议**：把 `os.open + _try_fcntl_lock + raise` 包在 try/except OSError 内，except 时先 `os.close(fd)` 再 raise；两处共享 try/finally 模式

## Follow-ups（合入后跟进）

### F-CR-015 · release 未 atexit.unregister（minor，critic 降级）

- **file**：`scripts/lib/path_lock.py:234-260`
- **依据**：`detailed-design.md:1266` release docstring "释放 fcntl + **解 atexit 注册**"
- **现状**：实现仅靠 `_released` 标志（路径 240-242）让 atexit 二次调用幂等无副作用，未调 `atexit.unregister(release)`
- **判断**：critic 降级 minor 合理——_released 兜底无功能副作用；但长进程内累积 atexit handler 是泄漏
- **建议**：release 入口 `_released` 检查后加 `atexit.unregister(release)`（Python 3.x 支持）

### F-CR-010 · _is_pid_alive 缺 pid<=0 guard（minor）

- **file**：`scripts/lib/path_lock.py:60-68`
- **现状**：POSIX `os.kill(0, 0)` 语义为"探测当前进程组"恒返 True；若 `lock_data.get('pid', 0)` 取 0 时 `_is_pid_alive(0)` → 残锁无法清理
- **建议**：函数首行加 `if pid <= 0: return False`

### F-CR-013 · _write_lock_json OSError 未包装 WorkflowError（minor）

- **file**：`scripts/lib/path_lock.py:82-95`
- **现状**：lseek/ftruncate/write/fsync 失败的 OSError 直接传播；`workflow_continue.py:259-266` 只 except LockBusyError + WorkflowError → traceback 泄漏到 stderr
- **建议**：`_write_lock_json` 加 `try/except OSError → raise WorkflowError(...) from exc`

### F-CR-001 · acquire 嵌套深度 4-5 层（suggestion）

- **file**：`scripts/lib/path_lock.py:155-214`
- **现状**：if-not-ok → if lock_data → if-not-pid-alive → if-not-ok-retry → if retry_data 5 层；可读但偏边缘
- **建议**：抽 `_retry_after_stale(fd, lock_path) -> LockHandle` 子函数承担残锁清理 + 重试，acquire 主路径降至 ≤ 2 层
